# REPORT-SPEC: the case-file report, the fix plan and the feedback step

Status: built. Parts 1 (`612c624`), 2 (`cb3630d`), 3 (`0ca5d01`), 4 (the checkpoint list, `a75963f`) and 5 (`698a282`) are done; see docs/HANDOFF.md rows 24-41 and 46. Owner decisions are in section 9. Follow docs/WORKFLOW.md (CEO protocol) and CLAUDE.md "Hard constraints". This file only adds to them.

## 1. Goal

A non-technical person who runs `wp-issue-diagnoser` must be able to read ONE page that answers, for each problem: what do I see, where is it, why does it happen, how sure are we, and what do I do. Today the page has overlapping sections (What is wrong, Summary, Findings, Verdict) that disagree. The detection and the "confirmed needs two independent checks" rules are correct and stay; only the page and the steps after it change.

Real case used as the acceptance example: a real site. `debug.log` repeats `PHP Fatal error: Uncaught Error: Class "Elementor\Core\Schemes\Color" not found in themes/unicamp/elementor/widgets/original/heading.php:48`; the live page answers HTTP 500; theme Unicamp 2.2.0, Elementor 3.35.7, WooCommerce 10.6.1; plus an advisory "outdated template override, 5 templates, Unicamp + WooCommerce".

## 2. Non-negotiable rules

- The tool recommends and writes plans. It NEVER applies a fix and never writes into the site. Third-party code (themes, plugins) is changed only through updates, a theme switch or a child-theme override, never by editing its files: the tool writes text, not patches, for third-party code.
- `validate.js` stays the only owner of CONFIRMED / REPRODUCIBLE / REJECTED_FALSE_POSITIVE. This work changes no status and no verdict rule. If a part seems to need a change there, stop and show the owner the diff first.
- Gate-off output stays byte-identical. The new layout appears only with the gate on.
- `findings.json` keeps every internal field and label. Internal words (ids like `theme:unicamp`, PROBABLE NEEDS REVIEW, oracle, recomputation, NOT_RUN, "gate", "null") never appear in reader-facing text. A scan test covers the reader-facing areas (whole terms, a short visible allow-list).
- The report stays a static, offline HTML page: no external resources, no `innerHTML`, no network, no server.
- Honest wording: never "your site is hacked" or "broken because of X"; "not confirmed" wherever it is true; never claim a class or function "used to exist"; a replacement for a missing class is shown only as "found in your installed <plugin>", never as a verified fix; where the tool cannot know something it says so.
- Never delete or weaken an existing test. Explicit staging, never `state/`, `reports/` or `projects/`. No push. One full run (runner, `scripts/run-full.sh <label>`) per part.

## 3. Order of work (build order)

1. Case-file layout, status line, the nine reader fixes (3.1)
2. Cause detail (3.2)
3. Choice step and FIX-PLAN.md, including the cracked-copy case (3.3)
4. Checkpoint list underneath (3.4, this is "step A")
5. Browser link and the feedback question (3.5): built LAST

Each part: plan (15 lines or fewer), multiple-choice questions for any wording, owner "go", builder, reviewer, runner, one commit, report back with the real output for the real-site case.

What the person experiences when it runs (differs from the build order): summary and link are printed, then "open in browser? [Y/n]", then the report is read, then the choice questions, then FIX-PLAN.md is written, then the improvement question.

## 4. The report page

```

           (a real site: "Home page shows a critical error"); never a cut of the person's text
STATUS     1 likely cause - 1 thing to check - 0 confirmed
           Looked at: your log, the live page, the code. Not looked at: a throwaway test copy.
           ("the code" is under "Looked at" only when at least one code file was read; a site folder without code
           files gives "Not looked at: the code", the checks that need code are NOT CHECKED "the site folder holds no
           code files, so no code was read", and the NOT TESTED label says it comes from reading the log only. When PHP
           files exist but none could be analysed (too large or not readable): "Not looked at: the code (N PHP files were
           found, but none was analysed)" and the reason "the site folder holds N PHP files, but none could be analysed, so no
           code was checked".)

WHAT YOU SEE        screenshot (if any) and the live check: "The live page answered HTTP 500"

CASE 1  LIKELY CAUSE (not confirmed)
  Where       theme Unicamp 2.2.0, heading.php, line 48 (code lines shown)
  Why         plain sentence: what the code asks for, what the installed plugin has,
              what happens next. Say plainly when it is NOT a hook or two-plugin conflict.
  How sure    found in your log N times, last seen <date>; file and line re-read; live page
              result. "Not confirmed by a second, independent test."
  What to do  ranked options, each with how to undo it (3.3)
CASE 2  SOMETHING ELSE TO CHECK (probably not the crash)
  e.g. the template override: which files, which versions, what can break (cart, checkout, layout)
CASE 3  (only when present) SIGNS THAT A COPY WAS MODIFIED (3.3)

WHAT WAS CHECKED   counts, e.g. 38 pass - 2 fail - 11 not checked - 3 also noticed (3.4); full list with --verbose
FOR A DEVELOPER    collapsed: stack trace, other files using the same symbol, replacement
                   candidates, timeline, technical evidence
```

The old "Findings", "Verdict" and "What is wrong" headings are replaced by STATUS and the cases. The counts have four states; the fourth is worded "Also noticed, probably not the crash": a check found something, but nothing ties it to this problem (5.4). The STATUS line of an empty case reads "0 likely cause - 0 confirmed. This does not mean the site is healthy." Case 3 is rendered only when data for it exists (Part 3). Components are listed inside the case they belong to (Elementor and Unicamp in Case 1, WooCommerce and Unicamp in Case 2).

### 4.0 A run with no site files (`--no-files`; built in S1a and S1b)
- The level is "NOT TESTED ON A COPY"; the label reads "NOT TESTED: what this report says comes from <what was really read>. It was not tried on a copy of your site." The list is built from the data: reading your log, reading the code, looking at the live page, the text of your screenshots, else "your description only". A log and the code together keep the old sentence ("reading your log and the code").
- "Looked at" names only what was read. Without a site folder "Not looked at" says "the code (no site files were given)". The missing list names the code of the site and a database export file.
- Every check that needs the code or the log is NOT CHECKED with the reason "no site files were given, so no code was read" (or "... no log was read"). The reasons "the site folder holds no code files" and "none could be analysed" stay for a site folder that was given.
- Zero checks ran (pass + fail + also noticed = 0, no cause found): the verdict is "Nothing could be checked", with a sentence from the data, for example "How sure we are: not at all. Nothing could be checked, so this report does not say whether your site is healthy: no site files were given, no log was read and no live check was run." With a live page loaded: "... the live page was loaded, but none of the 53 checks ran on it." This ending now appears only when the probe loaded a page but stopped early or was partial and found nothing, so no live check could give a result (since S3a-fix, c611e59, a complete probe on a 200 page gives 7 results and the verdict "No confirmed breaking cause was found", see 4.0a). The sentence "Nothing that was checked points at a cause" is never used when nothing was checked. A cause found by other means keeps its own verdict.
- **The reason after a stop (S4ab, S4ab-fix).** When the live check did not run at all, the sentence says why: "How sure we are: not at all. Nothing could be checked, so this report does not say whether your site is healthy: no site files were given, no log was read and no live page check ran (<reason>)." The reason is the same as in the live-check sentence of 4.0a: after the website's protection or rate limiting: "(the website's protection or rate limiting stopped the test, so no more requests were sent: <detail>)"; after a cooldown: "(an earlier run was stopped by the website's protection, so this run waited and sent no request)"; when the site could not be reached: "(the site could not be reached)". With no address, or with `--no-probe`, the sentence stays "... no live check was run." (the older text).
- NO site files, and (a loaded live page answered a status of 400 or more, OR at least one live check failed): the verdict is "A problem was seen on the live page", built only from true parts, in this order: "The live page answered with an error (HTTP <status>)." (every distinct status, from the probe data), "<N> live check(s) failed." (N from the check rows that read the live page), "No cause could be found from what was given." and what is missing ("To go further, give the site files and a log."; an item that was given is left out). Example: "The live page answered with an error (HTTP 500). 2 live checks failed. No cause could be found from what was given. To go further, give the site files and a log." It names no cause, plugin or theme, and never says "No confirmed breaking cause was found" or "Nothing that was checked points at a cause" (the summary data carries the same new sentence). It applies only when the old verdict would have been "No confirmed breaking cause was found"; a run WITH a site folder keeps the old wording exactly, and the zero-checks verdict above is unchanged when the page answered 200 and no check failed (S1b-fix).
- **A 4xx answer with no failed check (S4ab).** When every status of the loaded pages is a 4xx code other than 429, and no live check failed, the label names the code instead: "The live page answered with an error (HTTP 404)"; two codes: "The live page answered with an error (HTTP 403 and HTTP 404)". The sentence is the same as above ("The live page answered with an error (HTTP 404). No cause could be found from what was given. To go further, give the site files and a log."). A 5xx, a 429, a failed live check, or no status keeps "A problem was seen on the live page". The same label is used in the terminal VERDICT line, `issue.html` and `findings.json`.
- **The old 5xx sentence with a conflict line (S4ab).** With a 5xx page and a possible conflict line the sentence reads "The live page answered with an error (HTTP 500). No confirmed cause could be found from what was given; a possible conflict is listed below." (with failed checks: "... 2 live checks failed. No confirmed cause ..."). Without a conflict line it stays "No cause could be found from what was given.".
- The log step says "no site files were given, so no log could be read" and the "Custom code first" and "Component and feature index" steps say "no site files were given" (S1b-fix; before: "no local WordPress root was given (--root) ...").
- Without a site folder the report does not say "No error log was found on this site" and gives no WP_DEBUG advice as if the site was searched; it says "No log was read, because no site files were given." and what to do (give the site folder). The last terminal line says "Nothing on your site was changed."

- A log without site files (`--no-files --log <file>`, S1d, S1d-fix): level 2 ("NOT TESTED ON A COPY"); "Looked at: your log"; "Not looked at: the code (no site files were given), a throwaway test copy" (and "the live page" when no address was given); the label says "... comes from reading your log." The two checks that read only a log (memory or execution limits, a missing PHP extension) can run; their PASS reads "not found in the part of the log that was read". The other 51 stay NOT CHECKED. A log alone never gives CONFIRMED, REPRODUCIBLE or a "most likely" case, and the report never says that all secrets were removed. Only fatal and parse errors count; a name must be made of letters, digits, `.`, `_` and `-`, otherwise "no plugin or theme can be named".
- Label "The log shows a possible cause", one name: "The log shows a fatal error in a file of <name> (last seen <YYYY-MM-DD>)." (the date only when the log entry has one). Several names: "The log shows fatal errors in files of <A> (last seen <date>), <B> (last seen <date>) and <C>." At most 3 names, newest first, then "... and <N> more." Then "This is a possible cause, not confirmed: the code was not read and nothing was tested." (several causes: "These are possible causes, not confirmed: the code was not read and nothing was tested."), then "The log may also hold older errors, and the tool cannot tell if this is the error you see now." and "To go further, give the site files."
- A log check that found something (also when it shows as "also noticed") is a possible cause too: its own text, for example "The log shows PHP running out of memory.", then the same "possible, not confirmed" sentence. "No cause could be named from the log" never appears then.
- Label "No cause could be named from the log": "The last part of the log (up to 2 MB) was read. It has no fatal error that names a plugin or a theme. This does not mean the site is fine. To go further, give the site files." A fatal error that names no plugin or theme (core, mu-plugins, no file): "The last part of the log (up to 2 MB) was read. The log shows a fatal error, but no plugin or theme can be named from it. This does not mean the site is fine." An empty log: "The log file is empty. This does not mean the site is fine."
- Together with an error page or a failed live check the page part comes first, for example "The live page answered with an error (HTTP 500). 2 live checks failed. The log shows a fatal error in a file of <name> (last seen <date>). This is a possible cause, not confirmed: ... To go further, give the site files." under the label "A problem was seen on the live page, and the log shows a possible cause"; without a possible cause the label is "A problem was seen on the live page" and the log sentence above ("No cause ... named") follows the page part. S4ab: when the only error statuses are 4xx codes other than 429 (and no failed check) and a log has a possible cause, the label is "The live page answered with an error, and the log shows a possible cause" (the page part of the sentence is "The live page answered with an error (HTTP 404).", as above). Without a possible cause a 4xx page gets the 4xx label of 4.0.
- Refused log names (before anything is read): "The file <name> is not read: a database export, an environment file or wp-config is not a log. Give an error log, for example debug.log." and "The file <name> is not read: a packed file cannot be read as a log. Unpack it and give the .log file."; a missing file: "The log file <path> does not exist or is not a file."; a file that cannot be read: "The log file <path> could not be read (<code>)."

### 4.0a What the live page adds to a no-files run (S3a to S3c; built 2026-11-20)
Only a run WITHOUT site files. A run with a site folder has none of the fields and lines below and keeps its old wording. All of it goes under "WHAT YOU SEE" (terminal, `ISSUE-REPORT.md`, `issue.html`, `case_file.see`) and into `findings.json`; none of it is under the VERDICT line. The lines of this section do not change the verdict label or "how sure we are", with two exceptions: the quiet live page (S4c, below) and the 4xx, stop and conflict wording of 4.0 (S4ab).
- **Live page checks (S3a; `findings.json` `live_checks`: `total`, `gave_a_result`, `could_not_run`, `reason`, `sentence`).** "Gave a result" is PASS, FAIL or ALSO NOTICED, never NOT CHECKED; the numbers are counted from the real check rows, not fixed. Sentences: "7 of 7 live page checks gave a result." (all ran: no "could not run" part); "<N> of <T> live page checks gave a result. <M> could not run: <reason>. A check that did not run is not a pass."; and when no live check ran at all: "No live page check ran: <reason>. A check that did not run is not a pass." (never "0 of 7" for a run that sent no request: no address, `--no-probe`, a cooldown). A protection stop on the first load (for example a 429: the probe was started and stopped) keeps the "N of 7" form with the count, "0 of 7 live page checks gave a result. 7 could not run: <reason>. A check that did not run is not a pass.", and so does a site that could not be reached (S4ab-fix: "7 could not run: the site could not be reached.").
- **The reasons (`issue/checkpoints.js` `liveSummary`, `protectionReason`).** "no address was given"; "the live check was switched off"; "the page answered with an error (HTTP 500), so it was not loaded again at the other screen size" (a 500 page: 3 of 7 gave a result); "the result of the live page test could not be read" (an old issue folder whose `probe.json` has no usable `planned`); "fewer page loads were completed than planned"; for a stop the wording follows the TEXT of the stop reason: "the website's protection or rate limiting stopped the test, so no more requests were sent: <reason>" (rate limiting, challenge, captcha), "the test was stopped to keep the website safe, so no more requests were sent: <reason>" (server instability, connection resets), "the test was stopped, so no more requests were sent: <reason>" (any other reason: 403, Retry-After, unknown); for a cooldown (no request was sent): "an earlier run was stopped by the website's protection / to keep the website safe, so this run waited and sent no request" (or "an earlier run was stopped, so this run ..."). The same helper gives the reason of a live check ROW after a stop, in a run with or without a site folder; the old row text "the live page probe did not run (no address, not allowed, or switched off)" stays only where it is true; "the live page probe stopped early, so a quiet result cannot be trusted" stays where pages loaded but fewer than planned.
- **Plugins, theme and WordPress version from the page that was loaded (S3b; `live_signals`, built by `issue/live-signals.js`, no new request).** Sources: the addresses of the files the page loaded (same address only, status below 400: `/wp-content/plugins/<name>/` or `/themes/<name>/` and the `?ver=` value), the generator tag, and a fixed list of 6 page comments (Yoast SEO, Yoast SEO Premium, All in One SEO, WP Rocket, W3 Total Cache, LiteSpeed Cache). Lines: "The page says it runs WordPress <v> (from the generator tag, which can be hidden or changed)."; "The page loads files of: <plugin> (version <v> in the file address, which can be a cache number). Plugins that load nothing on this page are not shown." (several: "The page loads files of: <a> <v1>, <b> <v2> and <c> (a number after a name is a version from a file address or a page comment, and can be a cache number). Plugins that load nothing on this page are not shown."; at most 5 plugins, then "and N more"; at most 3 versions of one plugin, then "and N more"); "The page loads files of the theme: <theme> (version <v> in the file address, which can be a cache number)."; "A comment on the page names: <a> <v> and <b>. A comment is not proof that the plugin is active." Nothing found: no line.
- **Possible known conflicts (S3c, S3c-fix; `live_conflicts`, built by `issue/live-conflicts.js`).** Only plugins whose FILES the page loaded, by exact name, never by version; a name that a page comment alone gave never matches. Three entries of `data/known-conflicts.json` can match (`wp-rocket-with-incompatible-plugin`, `cache-plugin-with-elementor`, `multiple-full-page-cache-plugins`); any other entry, also a new one, cannot. The line: "Possible, not confirmed: the page loads files of <A> and <B>. What the source says: <the entry's cause text> [<the entry's own note on what the source does not say>] Source: "<title>" (<host>), checked <date>. This does not show that it causes the problem you reported. The page shows only plugins that load files on this page, so other plugins may exist that were not seen." A main plugin and up to 3 partners are named, then "and N more"; up to 3 lines, then "And N more possible conflicts."; a pair entry prints before a set entry, and a lower entry whose printed names are all covered by an entry that prints is skipped. It never says "installed" or "active", and never says what caused the reported problem.
- **Known limits of 4.0a (all by design or not yet done):** only the one page that was loaded is read; files from another host (a CDN) are not read; a plugin that loads nothing on that page is not shown; a version can be a cache number; a page comment is not proof; a conflict line needs both plugins to load files on the page (cache plugins often serve their files from the cache folder, which is not used as a source, so such a pair is often not found); the Elementor entry matches only `litespeed-cache` and `wp-rocket`, and the set entry only `w3-total-cache`, `litespeed-cache` and `wp-fastest-cache`, because only those names are in the entry's own claims (other names in the entry lists do not match, on purpose: fewer matches); the 6 comment samples in `scripts/selftest-live-signals.js` come from the plugins' documented output and were not checked on a live site; an old issue folder with no `planned` says "stopped early" on the check rows (safe, not exact). - **Quiet live page (S4c, S4c-fix; no site files, no log).** The page answered without an error, no live check failed, at least one live check gave a result, and the verdict would otherwise be "No confirmed breaking cause was found". ### 4.0b Load errors, browser errors, the new symptom and the masks (4i, 4a; built 2026-11-24 and 25)
- **The tool's own page load failed (4i-a; `lib/load-error.js`).** When the probe's own page load fails before a page answers, the live-check sentence names the reason in one fixed phrase and never the raw error text or the address: "0 of 7 live page checks gave a result. 7 could not run: the tool's own page load failed: certificate date error. A check that did not run is not a pass. This was one load, from one computer, at one time. It does not show what other visitors see." Phrases: certificate date error, other certificate error, wrong host name, connection refused, timeout, too many redirects, secure connection (SSL) error, connection reset. A date error is never called "expired". An error that is not in the table keeps the old reason "no page result could be used" (and not the one-load sentence); "the site could not be reached" is unchanged. The same phrase is in the zero-checks sentence ("... no live page check ran (the tool's own page load failed: certificate date error)"). The verdict label stays "Nothing could be checked"; retest cannot give FIXED_VERIFIED from a load error. The text first read from the probe error is only the part before " at <address>".
- **A browser error in the description or the screenshot text (4i-b; `lib/browser-error.js`).** A clue, always "possible", one fixed label per rule, and only for a run without site files: "Your description or screenshot mentions a browser error: <label>. Possible, not confirmed: this is a clue, not a cause." Labels: a certificate date error; a certificate error; the browser page "your connection is not private" (also "isn't private"); a "too many redirects" error; an SSL protocol error. It tolerates OCR damage (for example "NET:ERR_CERT_DATE INVALID"), needs a word boundary, and a log line gives no such clue.
- **The symptom answer (4i-c).** Question 3 ("What does the problem look like?") has a ninth choice, "The browser says the connection is not private" (id `connection-not-private`), right before "None of these"; the choices 1 to 8 keep their numbers. - **The placeholders (4a).** `[site address]` (the host of the address you gave, the path stays), `[email removed]`, `[IP address removed]`; the Limits line "Masking is best effort and pattern based; names can remain." appears only when something was masked. ## 5. Part details and acceptance

### 5.1 Part 1: layout, status line, nine reader fixes
(a) no "Nothing passed the gate"; (b) the cause sentence is identical in the case and in any summary line; (c) no internal values ("sandbox reproduction: null"); (d) never tell an HTML reader to "run with --verbose": name the advisory or show it collapsed; (e) resolution options agree with "What to do"; (f) confidence explained in a sentence; (g) "Not tested" lists only items tied to the problem; (h) title cut at a word boundary or written by the tool; (i) a very large log mostly noise: say what was read and skipped ("read 50 MB of 261 MB; your error log is very large, consider cleaning or rotating it"). Add the reader-facing term scan test.
Acceptance: the real-site report shows one status line, Case 1 with Elementor, Case 2 with WooCommerce, no contradiction, symptom reproduced agrees with the live check.

### 5.2 Part 2: cause detail
Under "For a developer" and summarised in Case 1: the exact symbol, file:line, a capped and redacted excerpt of the lines around it read from the copy, the call chain from the log's stack trace (function and hook names) when the trace has them, how many other files of the same component use the same symbol, and replacement candidates found in the installed provider plugin (read-only search; "found in your installed Elementor", with `verified: false` never shown as a fix). A small data file of known removed-to-replacement APIs may be added in the style of `data/removed-wp-functions.json` (source URL and claim phrase per entry). The report must say "this is not two pieces of code fighting over a hook" when that is true. Not known to the tool, so the report says so: which provider version still has the class.
Unverified assumptions to CHECK in the repo before relying on them: whether the real-site log contains a stack trace, and whether the installed Elementor has a replacement class (a guess is `Global_Colors`; do not state it unless found).

### 5.3 Part 3: choice step, FIX-PLAN.md, cracked copies
After the report, in the terminal (never with `--yes` or without a terminal): plain multiple-choice questions, "not sure" always allowed.
- Can you update the theme and plugins? yes / no / not sure
- Do you have a licence for the theme? yes / no / not sure
- Is this a copy, and do you have a backup? yes / no
- Which plan do you want? Only options still possible.
Default ranking when nothing is answered: (1) update the theme, if a legitimate update exists; (2) test with a default theme to confirm the cause; (3) a temporary older version of the provider, ONLY with evidence from the copy (a stated compatible version in the theme's own headers or changelog), otherwise "which version still has this is not known"; (4) a developer patch written as text for review.
FIX-PLAN.md contains: the problem in two lines; the chosen option and why (or "ranked default"); before you start (UpdraftPlus backup, work on a copy or staging, note current versions); numbered, checkable steps; an undo for every step; "done when" (page loads and re-running wp-issue-diagnoser no longer lists this cause); do-not list (no editing third-party files, no cracked-version workarounds). Written for a developer, with a short plain summary on top, and usable as a brief for Claude Code to follow on a COPY after a backup.
Cracked or nulled copies, as a visible case even when it is not the crash: report only SIGNS read from the copy (license-check code removed or pointing to an unknown domain, "nulled" or "cracked" in names or headers, obfuscated blocks, files not matching WordPress.org checksums where those exist, calls to unexpected domains). Wording: "signs that this copy was modified; it cannot be verified against the vendor". Advice: replace it with a licensed copy from the vendor. The tool never patches such code to make it run and never helps bypass a licence.

### 5.4 Part 4: checkpoint list (step A)
`data/checkpoints.json` generated from, and tested against, `docs/COVERAGE.md`: each of the 53 rows gets id, group, how (code, log, probe, config), breaks_site (yes / no / depends), and the name of its checker. A test fails if the two disagree or a claimed checker has no passing test. Every checkpoint ends as PASS, FAIL, ALSO NOTICED or NOT CHECKED with a reason ("no log", "probe not run", "copy skipped PHP"): ran and found nothing is PASS with a plain note; ran and found something that the crash evidence does not tie to this problem is ALSO NOTICED ("Also noticed, probably not the crash", never counted as FAIL); did not run or source missing is NOT CHECKED, never PASS. The page shows counts; the full list only with `--verbose`. Map existing checks onto it; add no new detection in this part (later: missing wp_head/wp_footer check, DISABLE_WP_CRON). No change to validate.js.

### 5.5 Part 5: browser link and feedback (built last)
After the run the tool prints a short summary and a link (`file:///.../issue.html`). With a terminal and not `--yes`: "Open it in your browser now? [Y/n]". It opens only a file from its own report folder. After FIX-PLAN.md: "Anything we should improve? (type it, or Enter to skip)" and an optional 1 to 5 score, saved as `feedback.md` in the same issue folder. Feedback stays on this computer and is never sent; it is redacted like logs (people paste private details). Last line: "Plan saved at <path>. To have Claude Code carry it out on a copy, give it that file."

## 6. Where questions are asked
Terminal first (reuses the existing question engine, skippable, no terminal mode). Buttons inside the HTML page or a local web server are NOT part of this work: the report must stay offline.

## 7. Tests
Every part: positive, negative and clean-site cases, using the exact real-site log line; the reader-facing scan; gate-off byte-identical; nothing written into the site (fingerprint before and after); `validate.js` untouched (or its diff approved first).

## 8. What stays out of scope
New detection beyond the nine fixes and the cause detail; the sandbox; a "guided local test" command; `.htaccess` reading; a REST probe; applying fixes automatically.

## 9. Owner decisions already made
- Questions in the terminal first, browser buttons later; ask before opening the browser, print the link either way.
- Open the page with what the visitor sees; the template override is its own case marked "probably not the crash"; the status line replaces Findings and Verdict; code lines and the stack trace sit collapsed under "For a developer".
- Default fix ranking as in 5.3; a downgrade only with evidence from the copy.
- Cracked-copy signs are an always-visible case with the "cannot be verified" wording.
- The tool never applies a fix.
- Feedback: a 1 to 5 score plus free text, saved locally as feedback.md; a closing line pointing to FIX-PLAN.md for Claude Code.
- Build order: the feedback step (Part 5) comes after the checkpoint list (Part 4).
