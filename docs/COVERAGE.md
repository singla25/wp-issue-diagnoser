# What wp-issue-diagnoser detects today (issue mode and the classic checks)

**Summary: 53 items: 19 DETECTED · 26 PARTIAL · 8 NOT DETECTED. 4 are reached only by the classic scan (`guard.js scan`, `checks/*`, Agent 2), not by issue mode; 41 are reached in issue mode (alone or together with the classic scan). Updated for step 5-A (rows 38, 40, 41), 5-B (rows 2, 3, 5, 6, 7, 33, 49, 50), 5-C (rows 24, 25, 26) and 5-D (row 20); only rules with a passing test are claimed.**

_This page is written by hand today. Checkpoint step A (see HANDOFF) generates `data/checkpoints.json` from it and a test keeps the two in step; until then a row is claimed only if a passing test exists._

_Most-likely-cause rule: a log fatal that names a class or function, whose file and line were re-read and which repeats, is shown at the top as "Most likely cause (found in your log)" even when nothing established it (never called confirmed); a probed 5xx page on a page the report is about is never "not reproduced" for a crash._

_Log fatal rule (after the copy fix): a "Class X not found" fatal that names a file can be CONFIRMED without the sandbox (issue/fatal-recheck.js, rules A and B in validate.js); a fatal beyond the last 2 MB of a large log is looked for with a capped deep scan when the problem looks like a crash._

_Copy rule (after step 8): the sandbox copy skips by FILE name (logs, dumps, archives, backups, keys, wp-config, .env, symlinks) and by tool folder only; a folder or PHP file is never skipped for being called debug, cache, upgrade or backup._

_Sandbox rule (after step 8): a sandbox that could not start or activate the site's plugins is "no sandbox evidence": the verdict equals the no-sandbox verdict plus a note. Only a sandbox that ran and did not reproduce the symptom can downgrade a finding._

**Step 7 (labels, the confirmed-and-breaking gate, Advisories) adds no detection row either:** it decides what is shown (`issue investigate --gate`) and labels it. It makes rows 30 and 31 reachable from a real crash (a log fatal naming a file now becomes a hypothesis), and rows 38 to 41 and 20 appear as findings only when the probe or the sandbox saw the effect.

**Step 6 (follow-up questions) adds no detection row.** It collects the facts that rows 20, 24, 25 and 26 depend on (the site's PHP version, which page redirects) and what the reporter saw (row 38 to 41), by asking, in plain language, at most 5 questions and never without a terminal.

Read from the code of this tool only (nothing was run).

**How to read the "Reached in" column.** *Issue mode* = `issue/*`, `probe/*` (the new flow). *Classic only* = `checks/*` through `guard.js scan` and Agent 2 (`agents/code.js`, `lib/wp-security.js`); issue mode never calls `checks/*`. *Both* = a version in each. *Neither* = not detected anywhere.

**Depth caveat for issue mode.** `issue/custom.js` builds a real syntax tree only for custom code (`customPaths`), all themes, and plugins the evidence names. Every other component gets the cheaper regex surface, and its duplicate declarations or hook removals are trusted only for names a log mentions. Where a row says "PARTIAL" because of this, the limit applies to the whole row.

**The sandbox bisection** (`issue/bisect.js`, Docker) can find *any* plugin combination that triggers the reported symptom, including conflicts this table says are not compared statically (duplicate constants, shortcodes, REST routes, AJAX actions). It does so only when Docker is available, the symptom reproduces, and an oracle can say so; it names the plugin set, not the mechanism.

## Top 5 gaps for a site that crashes, shows errors, or redirects

1. **Redirects: the loop/chain/cross-host judgement exists since step 5-A and `wp_redirect()` calls are mapped to their hooks since step 5-D (`5303b1d`); `.htaccess` is still not read.**
2. **(closed in step 5-A)** A blank page or critical-error text with HTTP 200 is now recognised by `generic` for the symptoms white-screen, redirect, other and connection-not-private.
3. **PHP-version breakage is only partly visible statically.** Removed functions and `Requires PHP` / `Tested up to` mismatches are checked since step 5-C (rows 24-26); `match` and typed properties on an older PHP are not. The sandbox runs one PHP version per build: WordPress images are pinned for PHP 8.2, 8.3 and 8.4 (`data/sandbox-images.json`, `matrix.php`; 7.4, 8.0 and 8.1 are not pinned), and there is no rerun on another PHP version (row 28). After a hosting PHP upgrade this is the usual cause of a crash.
4. **Third-party duplicates are compared only where the evidence points.** Duplicate constants, shortcodes, REST routes, AJAX actions and script handles are compared in issue mode since step 5-B (rows 2-3 and 5-7, `issue/custom.js`), and duplicate functions/classes between two plugins are compared only for names a log mentions (row 1). Without a debug log the answer depends on the Docker bisection.
5. **Environment and compromise causes reach issue mode only through log lines.** Memory/time limits and missing PHP extensions appear only if they were logged; `.htaccess`, `DISABLE_WP_CRON`, permissions, injected scripts (row 48) and cloaked redirects are classic-only or absent; obfuscated code and PHP in uploads reach issue mode through `issue/classic-adapter.js` (rows 49-50, step 5-B), so a "my site redirects to spam" report still gets no cloaked-redirect check.
