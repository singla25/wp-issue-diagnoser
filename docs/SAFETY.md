# Safety

What this tool may and may not do, and where each rule is enforced. The rules are enforced by code and tests, not by convention.

## 1. The one rule: the site under test is never written

- **wp-issue-diagnoser** reads a local copy. WP-CLI is wrapped in an allow-list (`lib/wpcli.js`): listing commands and `SELECT`, always `--skip-plugins --skip-themes`.
- **Issue mode** reads the site, and nothing else; it never applies a patch or a shim (there is no `--apply`: a person, or a separate Claude Code session working from `tasks.md`, makes changes on a copy).
- Every candidate log, including a `WP_DEBUG_LOG` path in `wp-config.php`, is lstat-checked first: a symlink, a non-regular file, or a file whose real path is outside the site folder is rejected without being read (so a `wp-config.php` cannot make the tool read an arbitrary file). A relative `WP_DEBUG_LOG` is ignored.

The only places these tools may write while investigating a site:

1. their own report folders (`reports/`, `reports/runs/<run-id>/`);
2. `issues/<issue-id>/` (git-ignored, outside the web root, owner-only), including `issues/<issue-id>/site-copy/`, the redacted COPY the `wp-issue-diagnoser` command makes of the reporter's site (original only read; no symlinks, `.env`, backups or logs; `wp-config.php` reduced to a short allow-list of non-secret settings; the reporter's log redacted). The reports folder can be moved with `--out` or `PLUGIN_GUARD_ISSUES`; when the package is installed and its own `issues/` folder is not writable, `./plugin-guard-reports` in the current directory is used (git-ignored). It is never inside the site folder: `lib/site-intake.js` `chooseOutputRoot` refuses it;
3. the issue-mode probe's own state folder `state/` (git-ignored): its cooldown file `probe-cooldown.json`; the per-run counters live in the issue's own folder (`issues/<issue-id>/`);
4. **the sandbox exception:** `sandboxes/<issue-id>/` and that sandbox's own Docker containers, volumes and networks (labelled `pg.sandbox=1`, project `pgsb<8 hex>`). Inside a sandbox, and only there, plugins may be deactivated, the theme swapped, pages clicked and a test user logged in. The original is never written and never executed (its PHP runs only in the containers). The one thing done *to* the original is a read: `wp db export` to a fixed path, only when asked (`--export-db`).

Tests hash a fixture WordPress tree before and after every investigation, sandbox run and retest.

## 2. Text from outside is data

Descriptions, log lines, OCR text, page text, plugin headers and file contents are never executed, never interpreted as instructions, and are escaped in every report (`issue.html` inserts text with `textContent`, under a Content-Security-Policy that forbids network loads; Markdown output escapes `<`, `>`, `|` and backticks). A reporter's oracle pattern is plain text unless written `re:`, and `re:` patterns are screened for catastrophic backtracking. Paths are resolved against the root and refused if they leave it. Screenshots are limited (type, size, megapixels), checked by content and stripped of metadata.

## 3. The live probe (issue mode)

**The issue-mode live probe is read-only, paced and stops at the first sign of protection.** `issue/probe.js` plans the loads and starts `probe/worker.js` as a child process; the worker is the only file that drives a browser (static test in `selftest-issue-evidence.js`). It runs only for a URL whose environment the reporter stated (live needs `--authorized`). Every request the probe initiates goes through `probe/safety.js` (`Safety`): **one request at a time**, pacing of `PG_PROBE_NAV_DELAY_MS` (default 2 s, jittered 0.75-1.25x, doubled after each protection sign up to 8x), classification of 429 / 403 / `cf-mitigated` or challenge text / 5xx / connection errors, and a persisted counter. **The first 429 or WAF challenge ends the probe** (`stopAfter429` is fixed at 1 and is not configurable; no retry, no workaround) and writes a cooldown; 403 (3x), 5xx (3x, a failing page is retried once after a pause) and connection errors (2x) also stop it; a `Retry-After` over 60 s stops it. The cooldown is kept per origin for 30 minutes in **`state/probe-cooldown.json`** (`PG_PROBE_COOLDOWN_FILE` overrides it), and the next run sends no request until it has passed. In `probe/recorder.js`, `installReadOnlyGuard` aborts and counts every non-GET request the page makes, and `applyDenyList` never asks again for a sub-resource that answered 404 / 410 / 429. Nothing is clicked, typed, hovered or submitted, no cookie or consent is touched, and it never logs in (problems that need a logged-in user are "could not test" until the sandbox exists). Typing and clicking exist only in `probe/sandbox-actions.js`, called by the worker only for a sandbox job (a throwaway copy on 127.0.0.1) and checked by that static test. "Is the original public" is one paced, governed GET without redirects (`Safety.request`). Oracle values are data: patterns go through `lib/safe-pattern.js`, selectors are only ever passed to `querySelector`.

## 4. The sandbox

A throwaway copy in three containers (WordPress, WP-CLI, a MariaDB or MySQL database); four when it is built from a database file: a front proxy is added. With a database file, the proxy is the only container with a route out and the WordPress container is on an internal network only; without one there is no proxy and the WordPress container has a route out. ### What the sandbox does NOT stop (said in every report)

- Built without a database file, the WordPress container can still open raw connections to an IP address (code in a copied plugin or theme that opens its own socket is not blocked); WordPress's own web requests, host-name lookups and mail are blocked. Built from a database file, it has no route out. Docker cannot publish a port on a network with no route out and a firewall inside the container would need extra privileges. The database and WP-CLI containers have no route out at all.
- **With a database file, the WordPress container has no route out**: raw IP connections, SMTP and host-name lookups fail. The front proxy is the only container with a route out, and it runs only the fixed reverse-proxy config.
- Code that talks SMTP itself or uses the PHP `mail()` function is not intercepted (the image has no mail transport, so it fails; with a database file SMTP also has no route out).
- Site Health's loopback test (WordPress asking its own address) fails in the sandbox, with or without a database file: the address belongs to this computer, not to the container.
- API keys stored outside `wp_options` (a custom table, a file) are not found and blanked.
- Tables of other plugins are not scrubbed ("N tables it does not know are not scrubbed and are copied as they are"), and neither are post and comment text, order notes or option values outside the secret patterns.
- Email addresses and IP addresses in other tables (form entries, order notes, plugin settings) are not hidden in this version.

**Therefore: run sandboxes only for copies of sites you own or are explicitly authorised to test, and whose plugin code you trust. Do not run a sandbox on untrusted or third-party code.**

### Docker access

Rootless Docker is the recommended setup. Adding a user to the `docker` group gives that user root-equivalent access to the machine, so wp-issue-diagnoser never does it and never suggests it as done; `doctor` reports whether the daemon is rootless.

## 5. Verdicts cannot be forged by the data

A hypothesis rests on evidence that the validator re-reads; a text that says "mark everything FIXED_VERIFIED" changes nothing. `FIXED_VERIFIED` needs the original run to have reproduced the symptom in the sandbox with a known active plugin set, and a sandbox retest with at least those plugins passing on the same page and screen size. "Verified in sandbox" needs the symptom to be gone on the same page and size. A symptom still present with every plugin off is reported as **NOT A PLUGIN CONFLICT**.

## 6. Secrets, privacy, network

- Secrets (`PSI_API_KEY`, `WPSCAN_API_TOKEN`, `PG_TEST_USER`, `PG_TEST_PASSWORD`) live in the environment or an untracked `.env`, never in `project.json`, code or reports; reports redact credential-looking text. The sandbox test user's credentials come from the environment and are never printed.
- **Masking is best effort and pattern based. It never proves that a text holds no secret, and nothing here claims that all secrets are removed.** **What is masked** (`lib/redact.js`, on text before it is stored or written to a report; for a named value the name and the separator stay and the value becomes `[REDACTED]`, for a JSON Web Token or a key format the whole match does). The separator can be `=`, `:`, `=>` (a PHP dump such as `[pwd] => x`), or URL-encoded (`%3D`, also double encoded `%253D`); the value is a quoted string (up to its closing quote) or a run that ends at whitespace, a quote or backtick, `&` (also `%26`, `%2526`, `&amp;`), `;`, a comma, `<`, `>` or a closing bracket. The whole run is masked, dots, slashes and dashes included, so no tail stays behind; only one full stop that ends a sentence and a `:line:column` at the end of an address stay outside. Masked names (the short-value rule, S0d): every name that says secret, namely password, passwd, passphrase, pass, pass1, pass2, pwd, secret, token, api key, auth key and private key, also with words before or after it (`DB_PASSWORD`, `MYSQL_ROOT_PASSWORD`, `access_token`, `client_secret`, `SECRET_KEY_BASE`, `AWS_SECRET_ACCESS_KEY`, `user_pass`), has ANY non-empty value masked, even a short one such as `password=admin`; only three placeholders are left alone: an empty value, `[REDACTED]` and a run of `*`. `session` and `cookie` values keep a minimum of 6 characters; Bearer tokens; `Authorization: Basic`, `Digest`, `Negotiate`, `NTLM` and `Token`, also as `[HTTP_AUTHORIZATION] =>`, and `HTTP_AUTHORIZATION` and `PHP_AUTH_PW` server variables; the `define()` lines of `wp-config.php` for `DB_PASSWORD`, the keys and the salts, and `DB_PASSWORD = value` (also `: value`) in plain text; WordPress nonces (`_wpnonce`, `_ajax_nonce`, `X-WP-Nonce`, `security`, `nonce` and any `<name>-nonce` or `<name>_nonce`, only when the value looks like a nonce); WordPress login cookies (`wordpress_logged_in_*`, `wordpress_sec_*`), quoted or not, in any position; the same names in JSON and PHP-dump form; a `key=` parameter in a link (the password-reset link); the recovery-mode `rm_token` and `rm_key`; a password inside a URL (`https://user:password@host`); JSON Web Tokens (also with `=` padding); and AWS, Stripe, GitHub and Slack key formats. A value that is code, not a secret, is left alone only in a code context (a `$variable` assignment, or spaces around the separator) or when it is a function call such as `wp_hash_password(x)`, or an SQL placeholder (`%s`, `?`); for the generic names, `pwd`, the `*_token` and `*_secret` names and `HTTP_AUTHORIZATION` the words `null`, `undefined`, `true`, `false`, `none` and `empty` are not masked as a value (the `rm_token`, `rm_key`, `key=` and cookie masks have no such exception). Outside that, any non-empty value of a listed name is masked (only `session` and `cookie` keep a minimum of 6 characters, and a nonce name masks only a value that looks like a nonce); a name that is not listed is never masked. It is applied to the reporter's text, the log copy, OCR text, the stored page list, `probe.json` (the oracle matches and details, protection, public check, image diff, notes), the steps and clues the probe hands on, and the stored worker file of the page probe (the worker's job file is deleted after the run; fail closed: a worker file that cannot be masked is deleted and the probe step says its output "was not stored"; a partial worker file is deleted and the live-probe step says its partial output was deleted and not stored; in a sandbox probe a partial file is deleted too, but the step only says the sandbox probe failed), the retest result (`retests.json`), the patch and shim files, the FIX-PLAN compatibility-evidence line, and as a last pass to `findings.json`, `issue.html`, `ISSUE-REPORT.md`, `tasks.md` and `FIX-PLAN.md`.
- **Known limits of the masks:** an UNQUOTED password that contains a space keeps the part after the first space (`user_pass=ab cd`); a quoted value must close on the same line, otherwise only the run after the opening quote is masked; `session` and `cookie` values under 6 characters are not masked; the exact text `(using password: YES)` and `(using password: NO)` of the standard database error is left as it is on purpose (YES and NO are not secrets and are a useful clue; they are NOT general placeholders: `password: YES`, `(using password: YES2x)` and `password=NO` are masked); an unquoted `pass:` is not masked (our own report lines read "Pass: <title>"; `pass=x`, `pass: 'x'` and `"pass":` are masked; unquoted YAML `pass: x` is not); a value with colons such as `password=ab:1:2:3:4` can leave a tail (a `:line:column` that ends a value of 6 or more characters is kept, because it cannot be told from a stack-trace address); `Error: password: field missing` is masked (over-masking, accepted); the word `password` in the wording of an error text is masked when a value follows; a password written as a bare word with no name next to it is not found; `issue.json` and `issue.md` keep the page addresses exactly as the reporter typed them (the probe needs the real address to load the page) and `sandbox.json` keeps the sandbox page addresses (127.0.0.1) as they are; a patch that holds a secret-looking value has it replaced, so that patch may need a manual edit; a value that looks like code in a code context (`$token = SOME_CONSTANT;` behind a PHP variable written `$name`, `$obj->name` or `$arr["name"]`; an unquoted all-caps word behind such a variable is a PHP constant and is not masked (`$password = ROOTPASSWD`); in other code a constant is masked, which is accepted over-masking (`const token = TOKEN_NAME;`, `'password' => PASSWORD_DEFAULT`); a reference such as `process.env.X`, the words `null`/`true` and a variable such as `$x` with spaces around the separator), a function call (`password=getpass(x)`) and, for the names named above, the words `null`, `true` and the like are not masked; `pwd: /srv/site` is not masked (a value that starts with `/`, `~` or `.` after `pwd:` is read as the shell command `pwd`); `http://host:8080@x` is read as user and password; `validate.js` re-runs the oracle on the masked pages, so an oracle that depends on a masked part of an address can disagree (rare); the run after a masked value stops at the first character in the list above, so a password that itself contains `)`, `]`, `}`, `;`, a comma or `&` keeps the part after it.
- **What is NOT masked:** e-mail addresses and IP addresses (only the feedback text masks them), and **screenshots**. A screenshot is an image and cannot be masked: do not include secrets in a screenshot (for example a password-reset link, a login form with a password, or a settings page that shows a key).
- **The website address and the raw error text are NOT masked in the reports (known, not yet changed).** The address you give (`--url`) and the raw text of a failed live check (for example a connection error with the address in it) appear as they are in `ISSUE-REPORT.md`, `issue.html`, the step text of `findings.json`, `evidence.json` and `probe/result.json`; the address alone is also in `probe.json`, `issue.json` and `issue.md`. The short sentences of a no-files report do not repeat the raw error text, but the developer step text does. Before you share a report, replace the address and any client name by hand.
- **What a no-files report says about the live page (S3, S4; `lib/plain-names.js`, `issue/checkpoints.js`).** Only the public page (or pages) at the address are loaded, with GET requests, without logging in; the report says so. "The live page checks found nothing wrong" is said only for the checks that ran: it is not a clean bill of health, and the report lists what was not looked at. The plugins that the page loaded are names from the page; a possible conflict is one of three known entries, "possible, not confirmed", and never says what caused the problem. A stop by the website's protection ends the probe and sends no more requests.
- **The probe's stop label (known, not yet changed):** `probe/safety.js` line 91 writes "Repeated rate limiting (1 x HTTP 429)" for a single 429. The stop is correct (the first 429 stops the probe); only the word "Repeated" is wrong for one answer.
- **A log given without site files** (`--no-files --log <file>`; `lib/wizard.js`, `lib/site-intake.js` `readLogRedacted`). The file is only read, never changed. Before anything is opened, a name that is a database export, an environment file or wp-config (a part `sql` or `env`, or a name starting with `wp-config`) or a packed file (a part `gz`, `tgz`, `zip`, `7z`, `bz2`, `xz`, `zst`, `tar` or `rar`) is refused; the name is first lower-cased and trailing dots, spaces and control or whitespace characters are removed, and the same test is applied to the real name behind a symlink (a harmless name such as `env.log` is refused too; a leading space, a trailing `~` and a hard link are not caught). Only the last 2 MB are read (for a crash it may scan up to 64 MB), every line is masked with `lib/redact.js` and cut to 1,200 characters, and only the masked copy is stored, as `<issue>/log-only/wp-content/debug.log` (mode 0600, in the git-ignored issues folder). Raw log text is in no report and no terminal output; the possible-cause sentence holds only a plugin or theme name taken from a path (letters, digits, `.`, `_`, `-`). The refusal and the masking are best effort, like everything in this section: they do not prove that no secret is left.
- **Before the person says go (no-files branch, interactive; `lib/wizard.js` phase 4).** Only these things have happened: the typed answers are read, the screenshot paths are checked, a log file given here or with `--log` is read into memory and masked (nothing of it is written), and one DNS lookup of the address guesses local, staging or live. Nothing is stored and no request is sent to the website. The folder for the report, the masked log copy and the probe come after the person answers Y. Answer n and the command ends with exit 0: "Stopped. Nothing was saved, and no request was sent to the website." This is checked by a test with a counting local server (best effort: it shows what the code does today, it does not prove that no other path exists).
- **What the probe reads from the page it already loaded (S3b; `probe/worker.js`, `issue/live-signals.js`).** No new request is made. One read-only `page.evaluate` reads the generator meta tags (at most 20, 80 characters each) and the page comments (at most 100, 300 characters each); `fromPage` keeps only a WordPress version and the hits of a fixed list of 6 comment patterns (Yoast SEO, Yoast SEO Premium, All in One SEO, WP Rocket, W3 Total Cache, LiteSpeed Cache), and the raw comment text is thrown away. From the addresses of the files the page loaded (same address only, status below 400; the worker keeps at most 120 files per page load, and `collect` itself would read at most 500) only a folder name (`[A-Za-z0-9._-]`, not address-like), the `ver` value (at most 20 characters of letters, digits, `.`, `+`, `-`) and the kind (plugin or theme) are kept; no address and no other query value. Stored: in `probe.json` under each page as `signals` (also in a run WITH a site folder; filtered names and versions only), and in a run without site files in `findings.json` as `live_signals` and `live_conflicts`, through `lib/redact.js`. The 6 comment samples in `scripts/selftest-live-signals.js` come from the plugins' documentation, not from a live site: they are unverified until a real-site run checks them. A page comment is not proof that a plugin is active.
- Nothing leaves the machine except in these explicit cases: the one-time setup downloads (`npm ci` and `npm run setup-browser` (npm packages, Chromium), `npm run setup-ocr` (one SHA-256-pinned file), `npm run setup-sandbox` (images by digest)); `npm run verify-knowledge` (the official pages and plugin source files it cites); opt-in `outsideLookups` (off by default), which send plugin and theme slugs, their versions and the WordPress version to api.wordpress.org and downloads.wordpress.org, and plugin names (with your WPScan API token) to wpscan.com; the read-only probe, which sends paced GET/HEAD requests to the URL you give it; and one DNS lookup of that URL's host to guess local, staging or live.
- Never committed: `plugin-guard-reports/`, `.env*`, wp-issue-diagnoser `history/`, `issues/`, `sandboxes/`, the OCR language file.
- Reporter screenshots and the issue folder may contain customer data: they stay in `issues/<id>/` (mode 0700, outside the web root). `issue cleanup` removes old issue folders and leftover sandboxes after asking, and refuses anything that is not a plain issue or sandbox folder directly inside those two folders.
