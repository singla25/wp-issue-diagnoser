# Safety

What these tools may and may not do, and where each rule is enforced. The rules are enforced by code and tests, not by convention.

## 1. The one rule: the site under test is never written

- **Frontend QA** sends GET-style page loads through the request governor. It never submits a form, logs in, clicks add-to-cart, writes to a site, or works around rate limiting or a WAF. On the first 429 / challenge it stops making requests.
- **Plugin Guard** reads a local copy. WP-CLI is wrapped in an allow-list (`lib/wpcli.js`): listing commands and `SELECT`, always `--skip-plugins --skip-themes`.
- **Issue mode** reads the site, and nothing else; it never applies a patch or a shim (there is no `--apply`: a person, or a separate Claude Code session working from `tasks.md`, makes changes on a copy).
- Every candidate log, including a `WP_DEBUG_LOG` path in `wp-config.php`, is lstat-checked first: a symlink, a non-regular file, or a file whose real path is outside the site folder is rejected without being read (so a `wp-config.php` cannot make the tool read an arbitrary file). A relative `WP_DEBUG_LOG` is ignored.

The only places these tools may write while investigating a site:

1. their own report folders (`reports/`, `reports/runs/<run-id>/`);
2. `issues/<issue-id>/` (git-ignored, outside the web root, owner-only), including `issues/<issue-id>/site-copy/`, the redacted COPY the `plugin-guard` command makes of the reporter's site (original only read; no symlinks, `.env`, backups or logs; `wp-config.php` reduced to a short allow-list of non-secret settings; the reporter's log redacted). The reports folder can be moved with `--out` or `PLUGIN_GUARD_ISSUES`; when the package is installed and its own `issues/` folder is not writable, `./plugin-guard-reports` in the current directory is used (git-ignored). It is never inside the site folder: `lib/site-intake.js` `chooseOutputRoot` refuses it;
3. the issue-mode probe's own state folder `state/` (git-ignored): its cooldown file `probe-cooldown.json`. It is NOT shared with `src/frontend`; the per-run counters live in the issue's own folder (`issues/<issue-id>/`);
4. **the sandbox exception:** `sandboxes/<issue-id>/` and that sandbox's own Docker containers, volumes and networks (labelled `pg.sandbox=1`, project `pgsb<8 hex>`). Inside a sandbox, and only there, plugins may be deactivated, the theme swapped, pages clicked and a test user logged in. The original is never written and never executed (its PHP runs only in the containers). The one thing done *to* the original is a read: `wp db export` to a fixed path, only when asked (`--export-db`).

Tests hash a fixture WordPress tree before and after every investigation, sandbox run and retest.

## 2. Text from outside is data

Descriptions, log lines, OCR text, page text, plugin headers and file contents are never executed, never interpreted as instructions, and are escaped in every report (`issue.html` inserts text with `textContent`, under a Content-Security-Policy that forbids network loads; Markdown output escapes `<`, `>`, `|` and backticks). A reporter's oracle pattern is plain text unless written `re:`, and `re:` patterns are screened for catastrophic backtracking. Paths are resolved against the root and refused if they leave it. Screenshots are limited (type, size, megapixels), checked by content and stripped of metadata.

## 3. The live probe (issue mode)

**The issue-mode live probe is read-only, paced and stops at the first sign of protection.** `issue/probe.js` plans the loads and starts `probe/worker.js` as a child process; the worker is the only file that drives a browser (static test in `selftest-issue-evidence.js`). It runs only for a URL whose environment the reporter stated (live needs `--authorized`). Every request the probe initiates goes through `probe/safety.js` (`Safety`): **one request at a time**, pacing of `PG_PROBE_NAV_DELAY_MS` (default 2 s, jittered 0.75-1.25x, doubled after each protection sign up to 8x), classification of 429 / 403 / `cf-mitigated` or challenge text / 5xx / connection errors, and a persisted counter. **The first 429 or WAF challenge ends the probe** (`stopAfter429` is fixed at 1 and is not configurable; no retry, no workaround) and writes a cooldown; 403 (3x), 5xx (3x, a failing page is retried once after a pause) and connection errors (2x) also stop it; a `Retry-After` over 60 s stops it. The cooldown is kept per origin for 30 minutes in **`src/plugin-guard/state/probe-cooldown.json`** (`PG_PROBE_COOLDOWN_FILE` overrides it; it is not shared with `src/frontend`), and the next run sends no request until it has passed. In `probe/recorder.js`, `installReadOnlyGuard` aborts and counts every non-GET request the page makes, and `applyDenyList` never asks again for a sub-resource that answered 404 / 410 / 429. Nothing is clicked, typed, hovered or submitted, no cookie or consent is touched, and it never logs in (problems that need a logged-in user are "could not test" until the sandbox exists). Typing and clicking exist only in `probe/sandbox-actions.js`, called by the worker only for a sandbox job (a throwaway copy on 127.0.0.1) and checked by that static test. "Is the original public" is one paced, governed GET without redirects (`Safety.request`). Oracle values are data: patterns go through `lib/safe-pattern.js`, selectors are only ever passed to `querySelector`.

### What the sandbox does NOT stop (said in every report)

- **Without a database file, the WordPress container can still make raw outbound connections** to an IP address: code in a copied plugin or theme that opens its own socket (cURL, `fsockopen`, `file_get_contents` on a URL with an IP) is not blocked, because Docker cannot publish a port on a network with no route out and a firewall inside the container would need extra privileges. `WP_HTTP_BLOCK_EXTERNAL` stops WordPress's own HTTP API; host-name lookups fail; mail is intercepted; the database and WP-CLI containers have no route out at all.
- **With a database file, the WordPress container has no route out**: raw IP connections, SMTP and host-name lookups fail. The front proxy is the only container with a route out, and it runs only the fixed reverse-proxy config.
- Code that talks SMTP itself or uses the PHP `mail()` function is not intercepted (the image has no mail transport, so it fails; with a database file SMTP also has no route out).
- Site Health's loopback test (WordPress asking its own address) fails in the sandbox, with or without a database file: the address belongs to this computer, not to the container.
- API keys stored outside `wp_options` (a custom table, a file) are not found and blanked.
- Tables of other plugins are not anonymised ("N tables could not be checked and are copied as they are").
- Email addresses and IP addresses in other tables (form entries, order notes, plugin settings) are not hidden in this version.

**Therefore: run sandboxes only for copies of sites you own or are explicitly authorised to test, and whose plugin code you trust. Do not run a sandbox on untrusted or third-party code.**

### Docker access

Rootless Docker is the recommended setup. Adding a user to the `docker` group gives that user root-equivalent access to the machine, so Plugin Guard never does it and never suggests it as done; `doctor` reports whether the daemon is rootless.

## 5. Verdicts cannot be forged by the data

A hypothesis rests on evidence that the validator re-reads; a text that says "mark everything FIXED_VERIFIED" changes nothing. `FIXED_VERIFIED` needs the original run to have reproduced the symptom in the sandbox with a known active plugin set, and a sandbox retest with at least those plugins passing on the same page and screen size. "Verified in sandbox" needs the symptom to be gone on the same page and size. A symptom still present with every plugin off is reported as **NOT A PLUGIN CONFLICT**.

## 6. Secrets, privacy, network

- Secrets (`PSI_API_KEY`, `WPSCAN_API_TOKEN`, `PG_TEST_USER`, `PG_TEST_PASSWORD`) live in the environment or an untracked `.env`, never in `project.json`, code or reports; reports redact credential-looking text. The sandbox test user's credentials come from the environment and are never printed.
- Nothing leaves the machine unless a project allows it (`outsideLookups`). The only commands that use the network are explicit: `npm ci` (npm), `npm run setup-ocr` (one SHA-256-pinned file), `npm run setup-sandbox` (images by digest), `npm run verify-knowledge` (the official pages and plugin source files it cites), and the live probe / frontend agent against the URL you give them.
- Never committed: `plugin-guard-reports/`, `.env*`, Plugin Guard `history/`, `issues/`, `sandboxes/`, the OCR language file.
- Reporter screenshots and the issue folder may contain customer data: they stay in `issues/<id>/` (mode 0700, outside the web root). `issue cleanup` removes old issue folders and leftover sandboxes after asking, and refuses anything that is not a plain issue or sandbox folder directly inside those two folders.
