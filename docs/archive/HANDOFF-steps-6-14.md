## 7. Step 6 status (follow-up questions)

**Done: `issue/questions.js`, wired into `issue investigate`. Step 7 is next.**
- **What it is:** a pure, rule-based, offline engine. Seven rules in a fixed priority order, each asked at most once: since / what changed (choices = installed components, ordered by header version then name; file times are display text only), which page, logged in or out, what looks wrong (may rewrite the symptom and a DEFAULT oracle, never a reporter's own), the site's PHP version, which page redirects, phone or desktop. Every question has plain wording (a test bans jargon), numbered choices and "0) Skip this question"; "stop" ends all questions.
- **Caps and passes:** at most 5 per run. 3 before the probe (rules 1-3 before `evidence.run`, rules 4 and 7 inside it through the new `beforeProbe` hook, after OCR and logs, so rule 4 can use them) and 2 after the code analysis (rules 5 and 6). After pass B the analysis is run again, offline: the probe is not repeated, every file is overwritten (a test shows two runs give byte-identical files), and it happens before the sandbox.
- **Never asked** without a terminal on both input and output, or with `--yes`, `--no-questions` or `--no-prompt` (the flags win even when a reader is supplied).
- **Answers:** saved in `issue.json` under `questions` (`asked: { id: { answer, skipped } }`, `stopped`, `viewports`), applied only through `store.applyQuestionAnswers`, which turns the issue back into the input of `normalise()` and accepts only `since, changedBefore, pages, needsLogin, symptom, oracle, phpVersion` (anything else, such as a status or verdict, is refused). A page must be a path or an address on the issue's own host. `needs_login` is tri-state through the questions block. Older `issue.json` files without the block still load (tested).
- **Rule 6 was narrowed** from the plan: it asks only when the report is about redirects (symptom `redirect`, or redirect words in the description); every site has some redirect code. **Rule 4** asks for symptom `other`, or for an error symptom (white screen, JavaScript) with no error clue; a layout or speed complaint has no error clue by nature. A "which page redirects" answer counts like the symptom "redirect" in the redirect join (`redirects.join` `reported`).
- **Tests:** `scripts/selftest-questions.js` (84 checks: every rule positive / negative / already answered, order and caps, skip, stop, end of input, invalid input, no terminal, the three flags, determinism, wording, other-host page refused, whitelist, old files, answers never change a status, idempotent re-run, and the whole `issue investigate` with a scripted terminal). Mutation checks: removing the whitelist, the host check, the caps or the flags-win rule each fails a test.
- **For step 8:** the interactive command calls the same `Q.runPass` with its own reader; the PHP version question is already there (decision 4 of the step-5 plan).

## 12. A log fatal "Class X not found" is reportable without the sandbox (after the copy fix)
- **Why a real site said "No confirmed breaking cause" (read-only investigation):** the fatal was never read. `debug.log` was 227 MB; the copy and `logs.js` read the last 2 MB, all "dynamic property" deprecation noise. In the original the exact fatal is there 33 times, all dated 16 Mar 2026, at byte ~295 KB (the START of the file). With the line in the text, parsing, the hypothesis (`missing-function`, log support, theme:unicamp) and the "backed by a log error" line already worked.
- **Deep log scan (`issue/logs.js` `deepScan`, `looksLikeCrash`):** only when the 2 MB tail has no fatal AND the problem looks like a crash (symptom white-screen, a clue of a critical error / fatal, or crash words in the description). 64 MB cap in 1 MB line-aligned chunks: 3/4 backwards from just before the tail, and, only if that finds nothing, forwards from byte 0 (a backwards-only scan would never have reached byte 295 KB). Keeps fatal-like lines only (200 max, 1200 chars, redacted, plus up to 6 stack lines). `logs.json` files[].deep and the `logs` timeline step say "the last 2 MB ... no fatal error, so N MB before it and M MB from the start were also read (X MB of Y MB): ...". Same function used by the wizard (`lib/site-intake.js` `readLogRedacted`): the found lines are placed at the END of the copied log, inside the 2 MB the analysis reads; the intake step records the same sentence. The wizard decides "crash" from the description words only (it sets the symptom `other`).
- **`issue/fatal-recheck.js`, called only from `validate.js`** (the sole owner of CONFIRMED): for a `missing-function` hypothesis whose log support is `php-class-not-found`, F:L is re-read (line +-2 must name X), the fatal must repeat (>= 2 identical entries). Rule A: + the fatal's timestamp within 24 h of `probe_ran_at` (new field in the ISSUE file, written by `probe.js`; NOT in `probe.json`, because `selftest-issue-graph` requires every work file to be byte-identical across investigations; the issue's creation time if no probe) + a 5xx on the same host. Rule B: + a full scan of all PHP of the copy (plugins, themes, mu-plugins, wp-includes: class / interface / trait / enum / class_alias) finds no definition, the copy skipped no PHP (`work/intake.json` `php_skipped`), every file was readable (< 2 MB), no component failed to parse, and X has a namespace. When a rule holds the log support is subsumed: the two supports are `fatal-site` + `probe-5xx` / `class-undefined` (total two, `independent_kinds` still has `log` so the gate sees the log fatal).
